# 个人 AI 会话群网页方案（待实现）

网页按工具 → 项目 → 会话显示，仅列出绑定个人 AI 会话群的会话。工具显示名为 Codex、Claude、Zcode、Kilo、Dsh。此文档描述方案，当前尚未增加网页或接口。

## 接入位置

```text
网页 ── HTTP / SSE ── 桥接服务 ── 统一 worker HTTP ── 原生工具
                         │
                         └── 飞书消息、群名同步
```

建议增加轻量的桥接网页入口。现有 `apps/web-app` 的聊天和侧边栏交互可供参考，但其后端当前直接面向 Codex；新入口通过桥接服务统一访问 worker。浏览器只持有网页登录凭据，worker 的 endpoint token 和飞书凭据留在服务端。

桥接维护绑定、路由、提交去重和群消息发送；worker 维护原生会话读取与执行；网页展示会话、发送消息和改名。网页写入也使用个人群的执行流程、队列与原生会话锁，避免网页和飞书同时写入时绕开既有规则。现有 A2A 接口用于会话共享，不能直接套用为个人群网页接口。

## 列表与身份

- 从个人群绑定和会话目录生成白名单，每次读取、发送、改名均检查绑定及账户身份；排除共享群、辅助入口、话题和已解散群。
- 会话身份使用 `profile + toolId + sourceId + nativeId`，项目使用工具账户及规范化工作目录；同名项目显示路径供区分。
- 默认显示活跃会话；worker 离线时保留已绑定项并标记不可发送。归档状态应来自现有目录及 worker 的能力，不能把读取失败当作已归档。
- 工具层从发现的 worker 及能力声明生成，不在网页后端增加特定工具的执行分支。

## 消息与名称

- 网页输入带唯一请求 ID，通过桥接提交至已绑定的原会话；飞书群以机器人消息标注“来自网页”。原生确认之前显示提交状态，不能只凭 HTTP 成功标记送达。
- 飞书输入、网页输入、原生工具输入和 AI 回复汇入同一会话视图。网页提交的 worker job 属于桥接来源，需由提交/回复链路同步到群，不能依赖仅回推原生来源的 `native-turn-sync`。
- 使用原生消息/轮次 ID 和提交 ID 去重；服务端共享观察结果，SSE 通知网页。断线后读取会话快照并恢复事件游标，避免每个浏览器独立高频扫描 worker。
- 网页改名交给现有名称同步协调器更新个人群及原生会话，并保存名称基线，避免下次扫描用旧名称覆盖。群/工具端改名沿用 15 秒扫描，再通知网页；同时改名沿用现有群名优先规则。
- 原生解析与来源识别继续放在 worker，桥接和网页仅使用统一数据格式。

## 当前能力与分期

Codex、Zcode、Kilo 已有统一 `conversation` 读取、原生输入回推和名称同步，适合先验证完整三端同步。Zcode 原生改名需要桌面配对模式。Claude、Dsh 已有历史、提交和名称接口，但当前 worker 尚未提供标准化 `conversation` 读取；若要求工具端主动输入也同步到网页及群，需要先在这两个 worker 补齐对话读取、终态和原生来源识别。

第一版范围：三级侧边栏、已有个人群会话的聊天、流式状态与回复、双向改名、离线提示。以每个工具现有能力决定可用操作。

集成验证沿用 autotest：网页输入到工具与飞书、飞书输入到工具与网页、工具输入到网页与飞书、三处改名、重复提交及断线恢复；测试结束仍归档会话并解散群。
